# 2026-09-20 - Adding the 32k DEM

Notes on how the high-resolution DEM layer was added, what was learned about the source data, and the decisions made along the way. Done by bburns with Claude Code.

## Source data

A folder of rasters exported from Unreal Engine (`lotr terrain/height_ue`):

- `MEDEM_x0_y0.png` ... `MEDEM_x7_y7.png` - 64 tiles, 8x8 grid, each 4033x4033 px, 16-bit grayscale PNG, 766 MB total.
- Also `ME10K.png` and `raw_height.jpg` (10000x10000) - checked and discarded: `raw_height.jpg` is pixel-identical to the existing 10k DEM, and `ME10K.png` is the same data with a brightness curve applied (every 8-bit value maps to exactly one new value), so neither adds information.

The original README todo mentioned a "40k x 40k DEM at 50m/px". This is not it - the mosaic is **32257 x 32257 px** (8 x 4032 + 1), giving **62.03 m/px** over the 2001 km extent. The files were briefly named `dem40k` because of that assumption, then renamed.

## Facts about the tiles (verified against the pixels)

- **Overlap**: adjacent tiles share one edge row/column (Unreal's 4033 = 4032 + 1 convention). Column 4032 of tile x2 equals column 0 of tile x3 at every sampled row.
- **Orientation**: tile x increases eastward, but tile **y increases northward** - the top row of tile y3 equals the bottom row of tile y4, so `y=7` is the top of the map. The build script maps tile y to image row `7 - y`.
- **Extent**: assumed identical to the 10k DEM. Confirmed by downsampling both to 800 px: correlation 0.989, and a red/green overlay fuses to yellow everywhere. The only visible disagreement is Mount Doom, which is painted brighter in the old 8-bit file.
- **Values**: 0 to 64727, mean ~10200. The relationship to the 8-bit DEM is a curve, not a constant: ratio ~224 at low elevations, ~365 mid-range, ~255 near the top (the old JPEG had a tone curve baked in). Colour-ramp breakpoints were therefore mapped through a measured table rather than scaled:

  | 8-bit | 16-bit |
  |---|---|
  | 0 | 0 |
  | 15 | 5166 |
  | 17 | 6063 |
  | 18 | 6479 |
  | 51 | 17575 |
  | 80 | 25596 |
  | 101 | 30393 |
  | 180 | 48800 (extrapolated) |
  | 220 | 56300 (extrapolated) |

- **Hillshade z-factor**: 0.4 on the 16-bit data gives the same relief as 100 did on the 8-bit data.

## Georeferencing

Derived from `10k/dem.wld` so the two DEMs overlay exactly: pixel size = 2001000 m / 32257 px, top-left corner = the 10k corner. Each tile gets a `.wld` sidecar; `gdalbuildvrt` mosaics them. Tagged EPSG:32631 to match the project CRS (used as a plain metric grid, as the vectors are).

## Output format and why it is four files

- Quadrant GeoTIFFs `32k/dem_nw|ne|sw|se.tif`, 16-bit, tiled, DEFLATE + PREDICTOR=2, internal overviews (2..64). 154-299 MB each, ~970 MB total.
- `32k/dem.vrt` (in git) presents them as one raster; QGIS opens it as a single layer with no visible seams.
- `32k/hillshade.tif`, 8-bit, JPEG-in-TIFF quality 85, overviews. 197 MB.

A single 966 MB GeoTIFF was built first. GitHub accepted the 197 MB hillshade upload in 3 minutes, but three attempts at the 966 MB file each transferred for ~17 minutes and then returned `HTTP 404` from `uploads.github.com` - a server-side timeout on long single uploads. Splitting into quadrants keeps every asset in the size range that works. (GitHub's hard limit is 2 GB per asset; that is not the constraint on a ~1 MB/s connection.)

GDAL's COG driver (`-of COG`) crashed on this machine with `ZSTDDecode: Data corruption detected` in its temp file, so the script uses plain GTiff + `gdaladdo` instead.

## Repository layout

- `data/rasters/10k/` - `dem.jpg`, `dem.wld`, `hillshade.jpg` (previously `10k.jpg`, `10k.wld`, `hillshade.jpg` at the top level).
- `data/rasters/32k/` - `dem.vrt` (in git) plus the five release files (gitignored via `data/rasters/32k/*.tif*`).
- `scripts/build-dem.ps1` - rebuilds everything from the 64 tiles; needs the GDAL that ships with QGIS.
- `arda.qgs` - the `rasters` group now holds `10k` and `32k` subgroups, each with `dem` + `hillshade` layers styled identically. Switch resolution by ticking one group and unticking the other. Layer ids were left unchanged so the label overrides in `arda_attachments.zip` still bind.
- Release `dem-32k-v1` - https://github.com/bburns/Arda/releases/tag/dem-32k-v1 - the five files, plain names, to be downloaded into `data/rasters/32k/`.

## Verification done

- Pixel values through the VRT equal the monolithic file at sampled points, including across quadrant seams.
- The project loads headlessly in QGIS 4.2 with all 24 layers valid, and renders through both groups with the same colour scheme; the 32k render shows individual ridgelines where the 10k one smears them.

## Loose ends

- The 40k / 50 m DEM the old README mentioned may still exist somewhere; if it turns up, it is one more folder under `data/rasters/`.
- `10k/dem.wld` is still "slightly off" as the README says; the 32k georeferencing inherits that, so fixing one fixes both.
- The original 64 PNG tiles are the true source and are not in the repo or the release. Keep them.
